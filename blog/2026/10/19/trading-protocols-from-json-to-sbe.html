The plumbing behind the trade: JSON, Protobuf, FIX, and SBE

October 19, 2026 · … min read
algorithmic-trading trading-systems market-microstructure IBKR JSON Protobuf FIX SBE execution

A strategy can look wonderfully intelligent in a notebook. It recognizes a temporary mispricing, calculates a position, and decides to trade. Then it leaves the notebook and meets a less glamorous collection of problems: network connections, broker sessions, message formats, acknowledgments, and the occasional timeout.

The market does not fill a backtest. It fills an order that actually arrives, passes the relevant checks, and finds someone willing to take the other side.

That makes the plumbing part of the strategy’s economics. An old quote can produce a bad decision. An order delayed behind a queue can lose its opportunity. An instruction whose outcome is uncertain can become a duplicate position if we retry carelessly. None of these failures requires the forecasting model to be wrong.

In my recent AI history post, the recurring lesson was that ideas and machinery have to fit each other. Here, the machinery is the conversation between a trading application, its broker, and the market.

Let’s unpack JSON, Protocol Buffers, FIX, and SBE, then put WebSockets, gRPC, ITCH, and OUCH on the same map. The aim is not to crown the fanciest acronym. It is to choose an interface we can operate correctly, at the speed and cost our strategy actually needs.

A reading companion, not a citation at every turn. Martin Kleppmann’s Designing Data-Intensive Applications, first edition (2017), Chapter 4, “Encoding and Evolution,” provides the broader framework for comparing formats and changing schemas. Chapter 8, “The Trouble with Distributed Systems,” is particularly useful when we reach timeouts, uncertain outcomes, and unreliable networks. It is not a trading manual, but those problems do not stop at the exchange’s front door (Kleppmann, 2017).

Why the wire can reach the P&L

Think of execution quality as everything that happens between “I want this position” and “this is the position I actually obtained.” A protocol does not create a forecasting edge. It can help preserve that edge, or make it surprisingly expensive to realize.

Engineering issue What a trading system experiences Possible economic consequence
Stale market data A decision uses a price that is no longer available. Worse fills or trading on an opportunity that has disappeared.
Slow order or cancel path An instruction reaches the broker or venue later than intended. Lost opportunities, worse queue position where time priority applies, or exposure that remains live longer.
Uncertain outcome after a timeout The application cannot tell whether an instruction was accepted. A blind retry can create additional exposure.
Incorrect units or precision Price, size, currency, or contract multiplier is interpreted incorrectly. Rejected orders or a position very different from the intended one.
Fragile recovery A restart loses track of open orders, fills, or positions. Unhedged exposure, duplicate orders, and reconciliation costs.
Overbuilt connectivity The team pays for complexity the strategy does not need. Higher operating costs without a compensating execution benefit.

Here is deliberately simple arithmetic, not a performance claim. A one-basis-point deterioration in execution on $1,000,000 of traded notional costs $100. If a strategy expected only two basis points before execution costs, one basis point is a rather expensive implementation detail. Whether a different encoding would recover any of it is an empirical question.

For a daily rebalance, reducing a parser’s work by a few microseconds may be irrelevant. For a latency-sensitive strategy, burst handling and tail latency can matter a great deal. In both cases, sending the wrong order quickly is still sending the wrong order.

First, separate the message from the conversation

We often call all of these things “protocols.” That is convenient shorthand, but it hides several different jobs.

Layer or concern The question it answers Examples
Business meaning What instruction or event is this? New order, cancel request, execution report, market-data update.
Encoding / serialization How do those fields become bytes? JSON, Protobuf, SBE, FIX TagValue.
API / session behavior How do we request work, track the conversation, and recover? REST-style endpoints, gRPC methods, FIX sessions, broker-specific API rules.
Transport and protection How do bytes travel, and how is the connection protected? TCP, UDP, HTTP, TLS; the exact stack depends on the service.

These are concerns rather than a rigid networking-layer chart. For example, HTTP is an application protocol, REST is an architectural style, and WebSocket adds a framed, bidirectional conversation over TCP.

Serialization simply means turning structured information into a representation that can be transmitted or stored. JSON is serialized too; binary does not have exclusive rights to that word.

JSON and the IBKR Web API: start with a message you can read

JSON (JavaScript Object Notation) is a text format for objects, arrays, strings, numbers, and a few other values. Its specification is pleasantly small; for financial applications, RFC 8259, Section 6, is especially worth reading because it discusses number interoperability and precision (Bray, 2017).

A simplified order-shaped message might look like this:

{
  "id": 7,
  "qty": 100,
  "priceTicks": 12345
}

Assume, only for this example, that one tick is $0.01. The price is then $123.45. This is a teaching example, not an IBKR order request: a real order needs the broker’s actual field names, instrument identifiers, required attributes, and validation rules.

IBKR’s Web API uses JSON requests over HTTPS. It gives us a concrete example of a readable message format wrapped in an HTTP-based API. Its order workflow also has brokerage-session requirements and response handling; “I received an HTTP response” is not the same as “my order filled” (Interactive Brokers, n.d.).

JSON strengths JSON trade-offs
Easy to inspect in logs and reproduce during integration. Field names and textual values add work and bytes compared with many binary representations.
Broad language support and familiar HTTP tooling. JSON itself does not impose the broker’s schema or business rules.
A practical fit for many broker integrations and moderate message rates. Numeric precision depends on how the receiving language parses numbers.
Quick to prototype and diagnose. Readability does not solve rate limits, authentication, order recovery, or stale data.

Do not conclude that JSON is “too slow for algorithmic trading.” Algorithmic trading includes a monthly rebalance as well as a colocated market-making system. Those are rather different engineering budgets.

For money and identifiers, make the representation explicit. Integer ticks, decimal strings, or a decimal type can be appropriate when the API contract supports them. Do not silently change a broker’s numeric field into a string because an article suggested that strings can preserve precision.

Protobuf: agree on the dictionary before sending the message

Protocol Buffers, usually shortened to Protobuf, is a schema-based serialization system. The sender and receiver agree on numbered, typed fields in a .proto definition. The wire representation carries compact field keys rather than repeating the full field names.

Our toy message could use this schema:

syntax = "proto3";

message OrderSketch {
  uint32 id = 1;
  uint32 qty = 2;
  int64 price_ticks = 3;
}

For the positive values above, its Protobuf payload can be written in hexadecimal as:

08 07 10 64 18 B9 60

That is a seven-byte toy payload, not the size of a complete trading request. It excludes framing, session metadata, authentication, and network headers. Field keys, variable-length integers, and length-delimited data are described in Google’s Encoding guide (Google, n.d.).

Where Protobuf fits at IBKR

IBKR’s API documentation describes Protobuf support in the TWS API, which connects over a TCP socket to Trader Workstation or IB Gateway. That is a different path from sending JSON to a Web API endpoint. Support and message coverage depend on the API and TWS/IB Gateway versions: verify the matching release documentation and supplied client rather than assuming every historical client or wrapper implements the same messages (Interactive Brokers, n.d.).

Using Protobuf here does not imply that the connection is gRPC. Protobuf is an encoding; gRPC is a separate RPC framework that commonly uses it.

Protobuf strengths Protobuf trade-offs
Typed schemas and generated code reduce hand-written parsing. Builds must manage schema files, generated code, and compatible runtimes.
Compact numeric encodings can reduce payload size. Binary captures need schema-aware tooling for meaningful inspection.
Supports controlled evolution across services and languages. Field numbering, presence, and default-value rules require discipline.
A useful choice for internal services as well as supported external APIs. It provides neither trading semantics nor order recovery by itself.

One particularly important evolution rule: do not reuse field numbers. Also distinguish “not supplied” from “supplied as zero” when the business meaning requires it; suitable field presence rules belong in the schema. Google’s proto3 Language Guide, particularly “Assigning Field Numbers” and “Specifying Field Cardinality,” explains these traps (Google, n.d.).

FIX: the trading conversation, not just a compact envelope

FIX (Financial Information eXchange) is an industry standard for communicating trading instructions and events. It gives counterparties a common vocabulary: a new order is not just an arbitrary object that happens to contain a price.

The familiar FIX TagValue representation uses numeric tags and textual values:

35=D | 11=7 | 38=100 | 44=123.45

Here, 35=D identifies a New Order Single, 11 is the client order identifier, 38 is order quantity, and 44 is price. The spaces and pipes are for readers. On the wire, fields use the SOH control character as a delimiter. This fragment omits required fields, headers, body length, and checksum; it is not a sendable FIX message. The FIX Trading Community’s TagValue standard documents the encoding (FIX Trading Community, 2020).

The more consequential part is the conversation around those fields. Classic FIX sessions use sequence numbers, logon/logout messages, heartbeats, and recovery procedures. Execution reports communicate order state and fills. A functioning integration needs the counterparty’s supported FIX version, message dictionary, session rules, and business conventions, not just a generic parser.

FIX strengths FIX trade-offs
Shared trading vocabulary across many brokers and venues. Each counterparty still has supported subsets, custom fields, and certification requirements.
Explicit order lifecycle and session-recovery mechanisms. Session state, persistence, replay, and duplicate handling add operational work.
TagValue is reasonably inspectable once the dictionary is familiar. Text scanning and conversion can cost more than a well-designed binary decoder.
Mature ecosystem of engines, monitoring, and operations practices. FIX is not a promise of the lowest latency, nor a universal plug-and-play connection.

IBKR also offers separately onboarded FIX connectivity. Its documentation describes an integration process involving its FIX Engineering team, with eligibility and commercial requirements. It is not a free format toggle for an existing Web API application; evaluate the current terms before making it part of the architecture (Interactive Brokers, n.d.).

FIX is not synonymous with TagValue. FIX business messages can have other encodings. That brings us to the acronym that is easy to transpose.

SBE, not SEB: a layout designed for predictable decoding

SBE means Simple Binary Encoding. It is a FIX Trading Community encoding standard designed with high-performance systems in mind. Like JSON and Protobuf, it serializes data; its distinguishing feature is the emphasis on native binary types and predictable field layouts.

Imagine a numbered form rather than a paragraph. For the fixed portion of a message, a decoder already knows where each box begins and what type it contains. It does not need to search for a textual key before reading the value.

The SBE 1.0 specification, especially “Field Encoding,” “Message Structure,” and “Schema Extension Mechanism,” explains both the efficiency goals and the constraints. The message header identifies the template and schema version; repeating groups and variable-length data have additional structure (FIX Trading Community, 2016).

For our toy order, a possible fixed root block would be:

Offset within the toy root block Field Type Example value
0 id uint32 7
4 qty uint32 100
8 priceTicks int64 12345

That is 16 bytes for this particular fixed block, before the SBE header and any outer framing. It is not a standard order template. Notice that it is larger than our seven-byte Protobuf toy payload: SBE is not a universal compression winner. Predictable access and low decoding overhead are different objectives from minimizing every byte.

SBE strengths SBE trade-offs
Fixed fields can be accessed without searching textual keys. Both sides need the correct schema and template definitions.
Binary numeric representations reduce text-to-number conversion. Raw captures are difficult to interpret without specialized tooling.
Generated codecs can support low-allocation processing. Schema changes must respect field placement, types, and versioning rules.
A good candidate for suitably designed latency-sensitive feeds and services. It supplies no authentication, transport, retransmission, or order lifecycle by itself.

Two caveats matter. First, not every SBE field is at one fixed offset throughout an entire message: repeating groups and variable-length fields still need traversal. Second, low-allocation or direct buffer access is an implementation property, not a promise that every SBE integration performs zero copies.

The schema may be described in XML, but that does not mean the live messages are XML. The dictionary and the encoded message are different artifacts.

Nor can we point an SBE client at any broker and expect it to understand. The endpoint must explicitly support that encoding, the relevant schema, and the required session or feed protocol. I am not presenting SBE as an IBKR Web API option.

More names worth placing on the map

The list expands quickly once we distinguish order entry, market data, and internal services.

Technology What it actually contributes Where it can help What it does not solve
WebSocket A persistent, bidirectional framed connection over TCP; messages may be text or binary. Streaming quotes and events without repeatedly polling an HTTP endpoint. Message meaning, feed-gap recovery, or proof that an order executed.
gRPC Typed remote procedures with unary and streaming calls; commonly Protobuf-based. Internal risk, portfolio, and execution services where supported. Automatic exactly-once trading effects or freedom from deadline and retry design.
Nasdaq TotalView-ITCH Venue-specific binary market-data messages. Reconstructing order-book activity from the documented feed. Sending an order to the venue.
Nasdaq OUCH A venue-specific order-entry protocol with order-status and execution messages. Eligible participants’ direct Nasdaq order connectivity. A universal market-data feed or a broker API available to every account.
CSV / XML Data formats, often encountered in files, reports, or schema definitions. Reconciliation, statements, batch exchange, or configuration. A live order session merely because they can represent an order.

For the connection and service distinction, useful primary reading is RFC 6455, Sections 1 and 5, and gRPC’s “Service definition” and “RPC life cycle” documentation (Fette & Melnikov, 2011; The gRPC Authors, n.d.).

For the venue distinction, Nasdaq’s TotalView-ITCH 5.0 specification, especially its Data Types, Add Order, and Modify Order sections, describes the feed; its OUCH overview describes order entry. Both require the appropriate access arrangements and surrounding connectivity. An ITCH payload is not inherently a complete reliable delivery system; the selected feed transport and recovery mechanisms matter too (Nasdaq, n.d.; Nasdaq, n.d.).

The dangerous message is sometimes the one you did not receive

Suppose we send an order and the connection breaks before the acknowledgment reaches us.

Did the broker never receive it? Did it accept the order but lose the return connection? Did an execution already happen? Locally, those possibilities can look identical.

A timeout describes what our application observed. It does not prove what the remote system did. This is where Chapter 8 of the reading companion earns its place beside the broker manual.

Classic FIX sequencing can detect gaps and support recovery, but session replay is not permission to submit a new economic order. Persist the relevant identifiers and state, handle permitted retransmissions according to the session rules, and reconcile executions and open orders. REST and proprietary APIs need equivalent business-level thinking even when their recovery mechanisms differ.

A client-generated identifier is useful, but it provides idempotency only if the server’s contract actually enforces the required duplicate behavior and retention scope. A fresh identifier can defeat that protection; reusing an identifier can also be invalid under some interfaces. Follow the specific contract rather than treating an identifier as a magic shield.

Other details deserve equally boring, equally valuable care:

  • Price and quantity units: ticks versus currency amounts, shares versus contracts, and multiplier conventions.
  • State transitions: transport delivery, broker acceptance, partial fill, full fill, cancel request, and cancel confirmation are different events.
  • Cancel/fill races: requesting a cancel does not guarantee that the order cannot fill while the cancel is in flight.
  • Feed gaps and slow consumers: detect missing data and backpressure; do not silently trade from an incomplete book.
  • Protection and audit: use the interface’s supported authentication and protected connectivity, restrict credentials, and retain useful records without leaking secrets.

Which would I choose?

Not “which is fastest in a blog post?” First ask which interface the broker or venue actually offers, then which one meets the strategy’s requirements.

Situation A reasonable starting point What I would verify before production
Research strategy or periodic rebalance through IBKR Web API / JSON, or the supported TWS API if its functionality is a better fit. Permissions, sessions, pacing, order responses, precision, and recovery.
Application built around TWS or IB Gateway Official compatible TWS API client, including its supported Protobuf messages. API/platform version pairing, callbacks, disconnections, and local state reconciliation.
Multi-broker institutional order management Supported FIX integrations. Counterparty dictionaries, certification, commercial terms, replay, and lifecycle semantics.
Internal typed services Protobuf, possibly with gRPC. Schema evolution, deadlines, allocation behavior, retries, and observability.
Supported low-latency feed or execution path The venue’s prescribed SBE or other native binary interface. Exact schema, access arrangements, transport, loss recovery, and burst behavior.
Direct Nasdaq integration ITCH for the relevant market data; OUCH for supported order entry. Entitlements, connectivity, session/feed specifications, and operational readiness.

These are starting points, not mutually exclusive architectures. One system might receive a native binary feed, use Protobuf internally, send FIX orders, and publish JSON to a monitoring screen.

Measure the system, not just the serializer

Before replacing an encoding, I would collect:

  1. Comparable timestamps: receive, decode, decision, risk approval, send, acknowledgment, and fill events. Use a monotonic clock for local durations and account for synchronization error when comparing different machines.
  2. Latency distributions: typical values and high percentiles such as p99 and p99.9, especially during realistic bursts, not just a quiet average.
  3. Resource behavior: actual message sizes, allocation pressure, CPU use, queue lengths, and dropped or missing updates.
  4. Execution outcomes: rejects, slippage against a stated benchmark, fill ratios, cancel outcomes, and the time needed to resolve uncertain orders.
  5. Failure tests: disconnect after sending, restart with live orders, replay messages where supported, and deliberately exercise schema-version mismatches.

A serializer microbenchmark can isolate a useful component. It cannot tell us how much end-to-end latency is spent in broker queues, risk checks, network transit, or venue matching. Nor is a fast acknowledgment automatically a fill.

The final accounting includes development time, certification, support, connectivity, and the cost of operating something we cannot explain at three in the morning.

Good plumbing does not predict the market. It preserves intent.

JSON makes an integration easy to inspect. Protobuf brings typed, compact messages. FIX gives trading counterparties a shared conversation. SBE emphasizes efficient binary layouts. WebSockets, gRPC, ITCH, and OUCH occupy other useful parts of the map.

None is a universal upgrade button. A format that saves decoding time but leaves us unable to recover an order has optimized the wrong problem.

The goal is simple to state and surprisingly demanding to implement: trade the intended instrument, at the intended size, under understood rules, and know what happened afterward.

That is not a decorative detail underneath an algorithmic strategy. It is how the strategy reaches the market.
